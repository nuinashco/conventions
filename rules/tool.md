TOOL-3, keeping a generated project on its template with `copier update`, is a rule of nuinashco/rnd-template, in the
[`.claude/rules/`](https://github.com/nuinashco/rnd-template/tree/main/template/.claude/rules) it gives every project.

### TOOL-1 MUST

`make check` runs ruff check, ruff format `--check`, `check-comments` and `check-conventions` on every Python file git
does not ignore (TOOL-4), pyright, `lint-imports` and pytest, and CI runs it on every pull request. pre-commit runs the fast
checks on the files of each commit, plus the commit-msg lint, nbstripout, gitleaks and the `uv lock` check.

*Why:* rules that a tool can check are enforced by a tool
([SWE at Google ch. 8](https://abseil.io/resources/swe-book/html/ch08.html)). A commit can skip pre-commit, and
pre-commit sees only the files it changes, so CI is where every file is checked.

*Check:* template.

### TOOL-2 MUST

Tool versions come from `uv.lock`. Hooks for Python tools are local `uv run` hooks, so pre-commit, CI and editors all
use the same versions.

*Check:* template.

### TOOL-4 MUST

The checks this guide adds on top of ruff are the `conventions-hooks` package of nuinashco/conventions. A repo opts in
with a `[tool.conventions]` table in its root `pyproject.toml`, where `ignore = ["STY-4"]` turns rules off for that
repo, and adds the package as a dev dependency pinned by `uv.lock`. The package's commands are `check-comments`,
`check-conventions`, `check-protected`, `check-commit-msg` and `review-comments`; `check-conventions` also checks
nuikit's FAM-2 and, in a project with a `src/<pkg>/paths.py`, rnd-template's ENV-1 and ENV-3. The checks run in three
layers with the same code: `make check` runs them on every file of the repo, locally and in CI (TOOL-1); pre-commit runs
them on the files of each commit; and the `conventions` Claude Code plugin gives Claude the findings while it works
(`PreToolUse` before an edit, `PostToolUse` after it, and `Stop` after it hands back: that hook runs in the background
and wakes Claude only when it has findings). The plugin runs the project's own `.venv/bin/<command>`, so each project
gets the version its lock pins, and does nothing in a repo that has not opted in.

*Why:* CI is the gate no author skips, pre-commit gives the same answer before a push, and feedback during the edit
is cheaper still. One plugin, enabled once per machine, serves every repo without copying hook settings into each.

*Check:* template; the opt-in and plugin tests of nuinashco/conventions.

### TOOL-5 MUST

Files nobody edits by hand are listed in `.gitattributes` with `protected=<why>`:

- `generated`: config mirrors, `.copier-answers.yml`, and whatever a build step writes;
- `vendored`: code copied in from another repo and changed only there;
- `published`: third-party files kept as published, such as `notebooks/reference/`.

The same lines carry `linguist-generated` or `linguist-vendored`, so GitHub folds those diffs in pull requests;
`.copier-answers.yml` alone stays unfolded, because a changed `_src_path` there changes which template the next
update runs. A
family item's mirror sits beside hand-written presets, so no path pattern can mark it: a leading comment line starting
`# Generated by` marks it instead. The `check-protected` Claude Code `PreToolUse` hook refuses an edit Claude makes to
any of them with its edit tools, giving the reason and the right place to make the change. It does not see shell
commands, so the commands that own the files (`make configs`, `copier update`) still write them. The hook fails open:
a broken environment lets edits through instead of blocking every one. Names carry no marker (no `_` prefix): `_`
means private in Python.

*Why:* agents fix whatever file is in front of them, and a refusal that names the source is the cheapest redirect.

*Check:* template; `check-protected PATH`.

### TOOL-6 SHOULD

A check that asks an LLM, such as a `claude -p` hook or a review subagent, is a judge and is built as one: narrow
criteria with named verdicts, an "unsure" outcome instead of a guess, a cited line for every finding, a fresh context
holding only the artefact and the rules, and structured output wherever code reads the verdict. It has a labelled set
of passing and failing cases, rerun whenever its prompt or model changes; every error it makes becomes a case. Anything
a script can decide stays a script.

*Why:* a judge's leniency or harshness shows only against labelled cases, and a narrow, cited criterion is easier to
align than a broad rubric ([Husain](https://hamel.dev/blog/posts/llm-judge/),
[Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).

*Check:* review; the plugin's judges are measured by `make test-judges` in nuinashco/conventions.
